# 印章文字识别接入

文析沿用 MinerU 的印章区域定位与专用 ONNX OCR，读取印文后交给现有 DeepSeek 字段链路，结果继续使用原文引用校验、人工核验、历史保存和导出。

## 处理流程

基础解析保持现有链路：文件检测、按配置进行页面方向与倾斜处理、MinerU 解析、原图坐标映射。字段名称不改变基础校正流程；专项能力只补充证据。

1. 云端适配保留 MinerU 返回的 `sub_type: seal` / `type: seal` 区域，包括没有文字的区域。不根据正文公司名推定印章。
2. 明确要求印章单位、名称、类别等印文时，在首次字段提取前调用专用 OCR；其他任务先使用基础结果，跳过印文识别。已识别区域复用缓存。
3. 现有 DeepSeek 字段批次理解自然语言和 Excel 要求。字段名为“企业名称”、要求为“以公章为准”时，可声明 `source_kind: seal`；正文缺失时可提出真实印章区域的 `recovery_refs`。这些声明只是候选来源，不是证据或执行指令，服务端仍检查区域、字段状态及预算。
4. 首次结果不充分时，最多补识别一轮。印文字段只走专用印章 OCR；正文金额、日期等只走普通局部文字 OCR。正文缺失且印章与现有正文文字块重叠时，服务端也可独立提出一次局部补识别，避免依赖模型主动请求。孤立印章不会触发无关字段补识别。
5. 补识别限定一个材料单元、一个能力、最多两个已定位区域和六个未解决字段。普通 OCR 读取候选区域附近的横向正文带，不重跑整份 PDF；新增可靠文字后才增加一次字段提取批次，未获得新依据时停止。
6. 首次已有依据的字段保持不变。补充结果仍需原文引用校验；未解决项、识别错误和模型失败保持缺失或待核验，不循环重试。补充来源附带原图坐标及核验说明。

专用印文 OCR 使用现有 MinerU `PPOCRv6ONNX(lang="seal")`，普通局部 OCR 使用同包 `lang="ch"` 和轻量文字检测模型；共享文字识别器，均在独立 CPU 子进程中运行，结束后释放。裁片最大边长 1,600 像素，坐标从实际校正页面转换回上传原图。

印文字段仅允许引用可靠识别的印章块，正文单位不能充当印文依据。普通局部 OCR 也不能升级为专用印文证据。印章真伪、签名身份、盖章位置关系与签章效力继续返回待图像核验。正文和印文重叠时，实际读出的文字归属仍需人工核对。

`document.capabilityPlan` 记录本轮启用、跳过与补识别原因，以及区域、字段和预算；跳过事件不计为能力调用。结果的 `sourceKind` 与 `recoveryRefs` 用于约束处理，不能代替实际文字引用。

相关实现：`service/seal_evidence.py`、`service/extraction_flow.py`、`regional_ocr.py`、`mineru_cloud.py`、`seals.py`、`seal_worker.py`、`semantic.py` 和 `grounding.py`。

## 范围和错误处理

- 当前补充识别用于文析的字段提取。Studio 的 OCR-only 准备和固定版本执行不自动启用，避免改变已发布规则的输入与输出；Markdown 全文也不回写本轮补充印文。
- 支持 MinerU 已定位的印章区域。漏检的印章不会由颜色、正文公司名或常量补出。
- 明确请求印文时每份最多处理 16 个印章区域；后续补识别另限两个区域且只有一轮。每次 OCR 工作进程串行执行，最长等待 60 秒；OCR 结束后释放子进程及模型内存。超过数量的区域保留待核验状态。
- 专用印文按 OCR 文字片段独立判断。分数不低于 0.85 的片段可进入正常引用校验；低分片段只作为候选，字段值与原始值留空，保持待图像核验。单位名称低分不会阻断同章内可靠的类别或编码。模型分数不是业务准确率。
- 重叠正文、浅印、黑白复印和残缺印文仍可能误识；区域引用通过不证明文字归属或业务含义一定正确，需人工核验。
- 模型缺失、校验失败、识别错误、超时或低置信度时，正文提取继续，印章区域保留供图像核验。有的印章读出、有的未读出时，已读内容保留并标记部分待核对。
- 签名和手写身份核验不由该模块处理。读出印章文字也不证明盖章有效或真伪。

## 模型和配置

本机默认复用已下载的 `.runtime/mineru-data/models/MinerU-4_models_onnx/OCR/paddleocr`。云端配置 `WENXI_SEAL_MODEL_DIR=/app/models/seal`，使用下列三份权重，共约 27.7 MB（十进制）。`WENXI_SEAL_OCR=off` 可停用专用印文 OCR，不影响普通局部文字补识别；保留印章区域和图像核验入口。

部署前可运行以下命令下载并校验到独立目录，再复制到构建上下文的 `models/seal/`。权重不进 Git，不在用户上传时联网下载。

```sh
.runtime/mineru-venv/bin/python deploy/live/prepare-seal-models.py \
  --output .runtime/deploy-seal-models
```

权重来自 [OpenDataLab 官方模型仓库](https://huggingface.co/opendatalab/MinerU-4_models_onnx)，固定版本 `358310b4f64b95f9fefc372ad899356e4111f376`：

- `seal_PP-OCRv4_det_infer.onnx`：4,769,171 字节，SHA-256 `3e190df84542c2756975febe8f73603b587a23c7f7badfdd3fc8a986540d5bc0`。
- `ch_PP-OCRv6_tiny_det_infer.onnx`：1,780,590 字节，SHA-256 `193bab7a04fca699a6c82e6abb5b81bdb28177f0abd4062552b04908dafb19f8`。
- `ch_PP-OCRv6_small_rec_infer.onnx`：21,159,378 字节，SHA-256 `5435fd747c9e0efe15a96d0b378d5bd157e9492ed8fd80edf08f30d02fa24634`。

每次工作进程启动均核验权重摘要。云端镜像在构建时预先生成紧凑识别图，运行时校验并复制到 `.runtime/wenxi-seal-cache`，减少首次识别时转换计算图的内存峰值；缓存损坏时从镜像修复。本机完整环境可使用既有持久化派生缓存。不修改原权重，字符表沿用锁定版本 MinerU 自带资源。

运行库沿用 `mineru==4.1.0` 和 `docvortex==0.6.8`。云端使用 `--no-deps` 安装这两个包，并明确列出 ONNX、几何处理等依赖，避免安装完整解析器的 PyTorch、VLM、Gradio 等运行栈。两套依赖清单均须进入构建上下文，不能直接对 `seal-runtime.txt` 执行默认依赖安装。

保留包内许可证、原作者说明以及公开文档中使用 MinerU 的标识。MinerU 的许可见安装包 `mineru-4.1.0.dist-info/licenses/LICENSE.md`，权重来源见上方官方仓库；印章检测和展平实现沿用 MinerU 中注明来源的 PaddleOCR 代码。本仓库不复制或重新分发这些第三方实现、字符表和权重。

## 验证记录（2026-11-04）

使用两枚程序生成的虚构圆形印章：一枚独立印章，一枚覆盖正文。原文公司为“星河演示采购中心”，印章单位为“星河演示科技有限公司”，章类别为“演示专用章”。两种名称刻意不同。

- 两枚印章的单位名称和类别共 4 项均由专用 OCR 读出。该结果不代表真实印章准确率。
- 使用生产相同的 1.5 倍页面预览生成裁片，运行真实工作进程，再执行两次 DeepSeek 字段提取。印章名称与类别均通过印章来源引用校验，正文申请单位保持独立；真伪字段保持待图像核验。
- 独立精简 Python 环境已验证完整 OCR 可运行且未加载 PyTorch。macOS 单线程进程峰值内存约 340 MB；另一次双线程试验峰值约 446 MB。
- 使用实际云端 Dockerfile 构建 Linux amd64 镜像，在只读根文件系统、1 核 / 512 MiB 限制下同时加载完整业务模块、页面方向模型并执行印章工作进程，两枚样例和缓存损坏恢复均完成，OOM 次数为零。构建阶段预生成紧凑识别图，避免首次上传时执行图转换。
- 进一步在 1 核 / 448 MiB 容器中完成两枚样例、缓存修复及 16 个重复样例印章区域的限量处理，OOM 次数仍为零。cgroup 记账包含文件缓存，实测触发过限额回收；该实验不等于所有真实大文档的容量保证，也不代表共享公网服务器已验收。发布前仍需检查目标服务器余量和其他产品负载。
- 页面验收使用独立本机端口重放上述真实结果，通过历史记录恢复后检查字段卡片、原图切换和印章高亮。旋转坐标另有离线测试。本轮没有重启用户正在使用的本机服务，也没有发布公网。

普通测试不加载权重、不联网、不调用付费模型。测试覆盖正文与印文互换引用、低置信度、真伪与签名边界、多枚印章部分失败、裁片回原图坐标、工作进程失败以及云端无字印章区域保留。

### 印文分段核验

- 专用 OCR 的每行生成稳定的 `父ref-s序号` 引用，保留 `sealParentRef`，使用实际行坐标及原图变换。旧任务中已保存的 `low_confidence` 印章也可按原有行分数投影，无需重跑 OCR。没有行信息的旧低分块仍只供图像核验。
- 模型仍使用原字段提取批次，分别匹配单位、类别、编码等字段。低分片段必须逐字引用真实 OCR 才能成为候选；伪造文字、正文替代或引用整枚章来绕过行分数会被拒绝。不会降低阈值或调用新识别服务。
- `candidates` 与 `value` / `raw` 分开保存。候选在界面中标为需核对，可点击定位；批量确认只处理正常待核验值。人工修改后显示核定值，保留原有机器结果和候选来源。
- 完整印文可以保留可靠摘录，并单独列出尚不可靠的片段。即使模型只返回了可靠部分，存在低分片段时也不能标为完整通过。印章真伪、签名身份和签章效力仍不进入文字候选流程。
- JSON 导出使用独立的 `recognition_candidates`；候选不进入 CSV 的字段值或原始值。历史快照原样保留候选和片段来源。

交互与模型协议验证使用原有虚构圆章的实际 OCR 文字，人工将单位名称片段的分数调整为 0.80，以重现不确定状态。一次真实模型批次返回单位候选、正常类别和部分印文；该实验验证分数分流及引用协议，不代表 OCR 准确率提升。未把用户上传的真实材料作为新模型测试输入。

本轮验证：197 项后端测试、85 项前端测试及 live/demo 构建通过。独立预览页检查候选定位、原图切换、批量确认排除候选，以及人工核定后保留原始值和候选。当前开发变更未重启本机服务、未发布公网；已有用户任务保持原状。
