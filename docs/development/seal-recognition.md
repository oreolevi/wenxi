# 印章文字识别接入

文析沿用 MinerU 的印章区域定位与专用 ONNX OCR，读取印文后交给现有 DeepSeek 字段链路，结果继续使用原文引用校验、人工核验、历史保存和导出。

## 处理流程

1. MinerU 返回 `sub_type: seal` 或 `type: seal` 的区域。云端适配现在保留无文字印章块，不根据正文公司名推定印章。
2. 从实际提交给识别引擎的校正页面裁切该区域。保留裁切边界，最大边长 1,600 像素。
3. 独立 CPU 子进程加载现有 MinerU 的 `PPOCRv6ONNX(lang="seal")`：专用印章文字检测、多边形展平、共享文字识别器。无需另开识别账户或调用新的云端 API。
4. 识别文字、置信度和多边形写回原印章块，保持原来的 `ref`。区域坐标仍对应校正页面，通过现有 `toOriginal` 映射回上传原图。
5. 印章名称、单位、类别、文字或编码等字段可进入原有 DeepSeek 提取批次。印文字段仅允许引用可靠识别的印章块，正文单位不能充当印文依据；普通正文字段也不能仅以印文证明正文主体角色。
6. 引用校验通过后仍是待人工核验。印章真伪、签名身份、盖章位置关系与签章效力继续返回待图像核验。

相关实现：`service/mineru_cloud.py`、`extraction.py`、`seals.py`、`seal_worker.py`、`semantic.py` 和 `grounding.py`。

## 范围和错误处理

- 当前补充识别用于文析的字段提取。Studio 的 OCR-only 准备和固定版本执行不自动启用，避免改变已发布规则的输入与输出；Markdown 全文也不回写本轮补充印文。
- 支持 MinerU 已定位的印章区域。漏检的印章不会由颜色、正文公司名或常量补出。
- 每份最多处理 16 个印章区域，串行执行，最长等待 60 秒；OCR 结束后释放子进程及模型内存。超过数量的区域保留待核验状态。
- 当前要求同一印章内所有非空识别行的置信度均不低于 0.85，才允许进入文字引用链路。模型分数不是业务准确率。
- 重叠正文、浅印、黑白复印和残缺印文仍可能误识；区域引用通过不证明文字归属或业务含义一定正确，需人工核验。
- 模型缺失、校验失败、识别错误、超时或低置信度时，正文提取继续，印章区域保留供图像核验。有的印章读出、有的未读出时，已读内容保留并标记部分待核对。
- 签名和手写身份核验不由该模块处理。读出印章文字也不证明盖章有效或真伪。

## 模型和配置

本机默认复用已下载的 `.runtime/mineru-data/models/MinerU-4_models_onnx/OCR/paddleocr`。云端配置 `WENXI_SEAL_MODEL_DIR=/app/models/seal`，使用相同两份权重。`WENXI_SEAL_OCR=off` 可停用补充 OCR；保留印章区域和图像核验入口。

部署前可运行以下命令下载并校验到独立目录，再复制到构建上下文的 `models/seal/`。权重不进 Git，不在用户上传时联网下载。

```sh
.runtime/mineru-venv/bin/python deploy/live/prepare-seal-models.py \
  --output .runtime/deploy-seal-models
```

权重来自 [OpenDataLab 官方模型仓库](https://huggingface.co/opendatalab/MinerU-4_models_onnx)，固定版本 `358310b4f64b95f9fefc372ad899356e4111f376`：

- `seal_PP-OCRv4_det_infer.onnx`：4,769,171 字节，SHA-256 `3e190df84542c2756975febe8f73603b587a23c7f7badfdd3fc8a986540d5bc0`。
- `ch_PP-OCRv6_small_rec_infer.onnx`：21,159,378 字节，SHA-256 `5435fd747c9e0efe15a96d0b378d5bd157e9492ed8fd80edf08f30d02fa24634`。

每次工作进程启动均核验权重摘要。云端镜像在构建时预先生成紧凑识别图，运行时校验并复制到 `.runtime/wenxi-seal-cache`，减少首次识别时转换计算图的内存峰值；缓存损坏时从镜像修复。本机完整环境可使用既有持久化派生缓存。不修改原权重，字符表沿用锁定版本 MinerU 自带资源。

运行库沿用 `mineru==4.1.0` 和 `docvortex==0.6.8`。云端使用 `--no-deps` 安装这两个包，并明确列出 ONNX、几何处理等依赖，避免安装完整解析器的 PyTorch、VLM、Gradio 等运行栈。两套依赖清单均须进入构建上下文，不能直接对 `seal-runtime.txt` 执行默认依赖安装。

保留包内许可证、原作者说明以及公开文档中使用 MinerU 的标识。MinerU 的许可见安装包 `mineru-4.1.0.dist-info/licenses/LICENSE.md`，权重来源见上方官方仓库；印章检测和展平实现沿用 MinerU 中注明来源的 PaddleOCR 代码。本仓库不复制或重新分发这些第三方实现、字符表和权重。

## 验证记录（2026-11-04）

使用两枚程序生成的虚构圆形印章：一枚独立印章，一枚覆盖正文。原文公司为“星河演示采购中心”，印章单位为“星河演示科技有限公司”，章类别为“演示专用章”。两种名称刻意不同。

- 两枚印章的单位名称和类别共 4 项均由专用 OCR 读出。该结果不代表真实印章准确率。
- 使用生产相同的 1.5 倍页面预览生成裁片，运行真实工作进程，再执行两次 DeepSeek 字段提取。印章名称与类别均通过印章来源引用校验，正文申请单位保持独立；真伪字段保持待图像核验。
- 独立精简 Python 环境已验证完整 OCR 可运行且未加载 PyTorch。macOS 单线程进程峰值内存约 340 MB；另一次双线程试验峰值约 446 MB。
- 使用实际云端 Dockerfile 构建 Linux amd64 镜像，在只读根文件系统、1 核 / 512 MiB 限制下同时加载完整业务模块、页面方向模型并执行印章工作进程，两枚样例和缓存损坏恢复均完成，OOM 次数为零。构建阶段预生成紧凑识别图，避免首次上传时执行图转换。
- 进一步在 1 核 / 448 MiB 容器中完成两枚样例、缓存修复及 16 个重复样例印章区域的限量处理，OOM 次数仍为零。cgroup 记账包含文件缓存，实测触发过限额回收；该实验不等于所有真实大文档的容量保证，也不代表共享公网服务器已验收。发布前仍需检查目标服务器余量和其他产品负载。
- 页面验收使用独立本机端口重放上述真实结果，通过历史记录恢复后检查字段卡片、原图切换和印章高亮。旋转坐标另有离线测试。本轮没有重启用户正在使用的本机服务，也没有发布公网。

普通测试不加载权重、不联网、不调用付费模型。测试覆盖正文与印文互换引用、低置信度、真伪与签名边界、多枚印章部分失败、裁片回原图坐标、工作进程失败以及云端无字印章区域保留。
